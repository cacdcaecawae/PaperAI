# Agent Note：PaperAI 在页面内解决草稿冲突

Status: implemented

[English](2026-09-21-paperai-conflict-resolution-in-the-page.md) | 中文

## 问题

一份文档有两个写作者：在分页页面里打字的人，和编辑同一个 `.docx` 的 Agent。当外部版本改动了某个已有未保存草稿的段落时，`restoreEdits` 把这条编辑标记为冲突，该段落冻结。在此之前这就是终点。冻结的段落仍显示草稿以便阅读，文案称草稿"保留供复制"，而出路只有两条：在别处重新手抄合并，或者一次性放弃全文草稿。对一段几百字的学位论文正文而言，"保留供复制"意味着作者手动选中、粘贴到另一个窗口、在脑子里对照两个版本，再把结果敲回来。

背后还有三个更小的洞。落在 `mapping` 之外的冲突段落——Agent 的改写加入了引注上标、公式或域——根本不接受任何按键，于是那句文案承诺了浏览器在任何地方都无法兑现的合并。`updateDraft` 拒绝丢弃节点已不可编辑的草稿，而那恰恰是这类改写的产物，于是文字被困在 store 里，再没有任何手势能清除它。真正属于冲突的两种失败——提交服务的 `NODE_TEXT_CONFLICT` 和工作台服务的 `changed; reload before applying`——都没有被 `actionErrorKey` 路由，于是双双落到泛化的"请重试"上，保存可以被按到天荒地老，却永远到不了那个能产生解决方案的刷新。

## 决策

**冲突段落本身就是合并区，上方的窄带是参照。** 一个 `div[data-paperai-conflict]` 被制造进页面，紧挨在该段落之前，引用文档当前的文字，并就地标出文档自草稿动笔以来改了什么。标记以两边共同的起点为准，而不是以草稿为准：作者自己的改动已经在下面那段里，两方对比会把它们说成是文档做的。用我的调用 `resolveConflict`，把这条编辑的 `baseText` 和 `baseRevision` 变基到当前文档上并清除冲突标记；该块离开 `conflicts` 集合，取得 `contenteditable="true"`，作者用书写其他每一段所用的同一套光标、输入法、撤销栈和格式栏继续往下写。没有第二个编辑器，没有 textarea，没有模态框：这个功能是一个标记位加一件页面家具。用文档的恢复该块的原始镜像并上报，于是这条编辑自行消失；它走 `finish` 而不是 store 重绘，因此进入 `history`，让一次销毁草稿的按压距离 Ctrl+Z 只有一步。这次撤销会把草稿连同窄带一起、以冲突状态还回来：控制器把作者放下的冲突草稿与接下它的那一页的文档和修订号一起保存，那一页撤销 用文档的 并上报同一段文字时就把它原样还回；切到别的文档再切回来也是如此，因为保留的预览连同撤销栈一起保留。页面会把这次上报标明为撤销，因为单凭文字分不清它和一次让文字保持不变的格式编辑，后者仍是一条新草稿。若作为新草稿还回，它会在未经询问的情况下变基到 Agent 的文字上，保存 会让它覆盖 Agent 的段落，而作者从没按过 用我的。

**窄带永远不会变成论文正文。** 它不带 `data-path`，因此 `mapBlocks` 无法识别它、`report` 无法从中读出草稿、`find` 也永不落入其中；它不带 `data-paperai-change`，因此变更导航跳过它；它是 `contenteditable="false"`，而 `beforeInput` 以拒绝任何范围未完全落在映射块内的输入为其背书；`sanitize` 会从 Host 送回的任何内容里剥掉除 `-change` 之外的每一个 `data-paperai-*`，所以窄带只可能来自浏览器。它的引文是一个 `p`，为的是继承文档自身的字面与行距——那正是两段文字可以竖直对读的原因——这也意味着 `blocksOf` 会返回它；今天没有任何代码在已落座的窄带上运行 `blocksOf`，因为唯一的调用方会先重建容器，而构造函数自身的文档把这一点作为警告写明。

**标记在它不再起作用的地方停下。** `wordDiff` 增加一个上限参数：`TOKEN` 把每个汉字算作一个词，于是两段 600 字的正文就是 360,000 个格子，而既有的 250,000 上限会把最寻常的中文冲突渲染成一整块删除加一整块新增。窄带传入 1,000,000，它负担得起，因为它只对一个段落按需运行一次，而版本比较要对每个改动段落都运行。当可识别份额低于 35% 时，窄带完全放弃行内标记，直接印出文档的句子，因为一次真正的改写会把单字"相同"孤岛撒遍整个结果，标记恰恰在最需要它的地方变成麻点；此时头部读作 文档把这段整个重写了，而辨识仍落在它本来就依靠的东西上——底色、竖线、无衬线标签和按钮。当文档里这段的文字仍是草稿动笔时的原样，标记同样停下：此时冲突在格式上，任何词级差异都显示不出来，而拿这些文字去标作者自己的改动，会把它们说成是文档做的。窄带用文档自己渲染出的 run 印出原文，让这次改格式本身就显示在窄带上，头部读作 文档只改了这段的格式，文字和你动笔时一样。冲突标记会比引起它的那个 revision 活得更久，所以当文字和格式都和草稿动笔时一样，说明文档已经把改动撤了回去，窄带改读 文档改过这段，现在文字又和你动笔时一样。

**浏览器无法编辑的段落得到一条诚实的窄带，而不是一句空头承诺。** 每个被识别的块现在都在 `data-paperai-node` 里写明自己的节点，无论是否进入映射，这正是让无法合并的冲突有处落座的原因。它的窄带逐字引用草稿，配 复制草稿 和需按两次的 放弃这段草稿，并且不带 用我的，因为没有任何按键能落到那里。被删除或无法匹配的段落没有可承载窄带的块，因此窄带显示在第一页纸面的最上方、第一段之前；放弃这一条不会影响其他草稿。窄带从不进入表格，因此单元格的窄带立在整张表格之前，并写明它对应第几行第几列。由于窄带可能离光标很远，待保存条会显示冲突数，点一下就把下一条窄带带进视野，并把焦点放在它的第一个按钮上。`updateDraft` 现在永远允许丢弃草稿；写入草稿仍然需要一个接受写入的块。若段落在文字不变的情况下变成浏览器无法写入的段落，比如外部修改只加了一个上标、一个域或一个链接，预览会把这条草稿标为冲突并给它这种窄带：仅凭文字判断会让它保持干净，既不在页面上，也走不到保存。

**要与草稿对读的东西随纸缩放，作为控件的东西不随。** 窄带位于携带 `zoom` 的 `.paperai-doc` 内。它的引文继承该缩放，因为一段清晰的参照压在一段缩小的草稿上，等于要求眼睛跨两种尺度比对。它 13 px 的标签和 28 px 的按钮除以 `--paperai-page-relief`——在同一个 `fit()` 里紧挨缩放写成 `1 / factor`——因此在任何缩放下都保持屏幕尺寸：否则 50% 适配下的 28 px 按钮只有 14 px 的点击目标。这个倒数通过每条声明上的 `calc()` 施加，而不是嵌套 `zoom`，后者会在可编辑宿主内部再套一层坐标系，而有三处 `getBoundingClientRect` 调用在读它。

**画在纸上的标记用纸自己的墨。** 两个 token，`--paperai-page-accent` 和 `--paperai-page-loss`，在两套配色里各持一个值，因为纸在两套配色里都是白的，而 app 的金色在暗色下解析为香槟色 `#e2b457`——在白底上是 1.9:1。同一轮审查纠正了这个页面上已经在发的两个缺陷：待保存的 `✎`、当前变更描边和光标把那个金色别名画到了纸上；比较页的 `ins`/`del` 底色在暗色下解析为 `green-900`（白纸上近乎一块黑），以及一个两套配色里都未定义、因而被静默丢弃的 token。两种标记现在都同时携带形状与颜色——退后并划掉，对比前移并加下划线——窄带的图例再用文字把它们说一遍。

渲染字符格式变化也必须由作者选择。预览将草稿原始有效 run 与新版本的渲染结果比较，并通过 `updateDraft` 记录冲突，直接保存也不能跳过选择。草稿的所有 run 和拆分段落均保持完整。把当前第一个 run 的格式复制到整份草稿会丢失混合格式，也不能代表任一作者的选择。保留草稿会接受当前 revision，并以该版本为基准记录格式，后续按键不会重新触发同一次冲突。比较的只有六种字符属性：加粗、倾斜、下划线、字号、颜色和字体。外部加上的高亮、删除线或隐藏文字不会引起冲突，重绘会把它们藏起来，保存时作者新写的字会带上它们；代码里以 TODO 标出了这一点。

## 备选方案

**一个并列两版并带合并框的侧面板。** 这是熟悉的形状，也是设计评审中唯一完整存活的方案。它同时意味着再造一个编辑器：合并框需要自己的输入法处理、自己的撤销、自己的格式，而且它把文字与它所属的页面分开，那正是这个产品存在的理由。窄带复用每一件已有的编辑机件，一件也不新增。

**模态冲突解决器，一次一段。** 它能给工作排序，也能从容展示三栏。它同时会让写作停下，而一份从长时间 Agent 回合归来、带着四处冲突的文档，会在打出第一个字之前变成四个模态框。

**只在页边留一道冲突标记，把两版文字交给版本面板。** 这是改动最轻、也最能保持页面安静的做法。它同时把真正的比对留在另一个界面、两次点击之外，而那正是本决策要终结的处境。

**入场和退场都做动画。** 入场做动画，因为窄带是不请自来的，它把论文正文往下推。而每一次退场都紧跟在对这条窄带自己按钮的按压之后，因此那是直接反馈，而不是一个区块在活动光标上方凭空消失；直接移除不需要 `transitionend` 记账，也不需要兜底定时器。

## 测试

`preview-html.client.spec.ts` 覆盖汉字分词输入上的上限、两种窄带形态、让窄带无法混入正文的三处缺席、改写回退，以及一侧被清空的情形。`editor.client.spec.tsx` 在真实 shadow root 上驱动四种按压：用我的 解冻段落且下一次按键上报草稿，用文档的 距作者的文字只有一次撤销，放弃这段草稿 问两次并在别处点击后复位，以及 复制草稿 选中引文——于是剪贴板被拒时 Ctrl+C 依然可用。`controller.client.spec.ts` 覆盖变基、它的三种拒绝、丢弃一条所在块已不可编辑或已离开文档的草稿、被放下的冲突草稿在页面重建或全部放弃之前都会以冲突状态回来，以及只剩冲突时 Ctrl+S 说明为什么什么都没保存。待保存条的冲突数跳到窄带、单元格窄带写明所在单元格，由 `editor.client.spec.tsx` 覆盖。`components.client.spec.tsx` 覆盖按网关实际送达原文写的冲突失败：它们路由到 刷新，只有保存之后才承诺窄带，其他操作之后不承诺；两种形态的落座、段落变得无法写入的草稿、选边之后的光标，以及对比页面上不带冲突，由 `editor.client.spec.tsx` 驱动。编辑器与控制器的联动测试覆盖混合 run 与拆分段落的仅格式冲突、选择前拒绝保存、两种选择，以及复制或单独放弃已删除段落的草稿。

## 影响

冻结块的文案退役：`editor.conflict` 和 `block.conflicted` 不再说草稿"保留供复制"，因为复制已不再是作者对它做的事。[写作流程决策](2026-09-12-paperai-writing-workflow.zh.md)拥有草稿冲突，其中那句冲突描述在同一次改动里被更正：它仍在描述"较新的 revision 使文字未动的草稿进入冲突"，而 `restoreEdits` 在编辑安全那一轮改为由文字单独决定之后就不再那样做了。草稿所在段落中文字看不出的变化，也就是渲染格式，或浏览器无法写入的内容，改由预览判为冲突，如上所述。跨到更新的 revision 时，若草稿动笔时的文字在另一个同类型的节点里也出现，`restoreEdits` 同样把它判为冲突：Host 会把节点 id 交给文字相同且距离最近的段落，于是在两个空段落上方插入内容会让它们互换 id；这种窄带请作者确认位置。

`resolveConflict` 是一个纯客户端 store 操作，背后没有 Remote 方法。提交服务自己的 `baseText` 校验正是这次变基要满足的对象，而它仍然是权威：一条变基后的草稿若在第二次竞争中落败，会再次冲突，窄带也会再次出现。这次拒绝以 `internal: <message>` 的形式到达浏览器，因为网关只转发 Host 失败的消息、不转发错误码，所以 `actionErrorKey` 匹配的是提交服务的消息原文（`text changed since the`、`head changed:`），以及工作台自己的 `changed; reload before applying`；改动 `commit-service` 里的这些措辞，就得同步改这个匹配。导出、校验、恢复或模板操作也会以同样的方式被超越，但它们只在没有草稿时运行，所以提示只要求刷新，不承诺窄带。

窄带是被制造进投影、而绝不进入 `.docx` 的浏览器家具，打印时隐藏。它不在 `.page` 上设置任何东西：office-cli 用 `min-height` 给页面定高，所以携带窄带的页面会随之生长，而页面自己的 `overflow-x: auto` 让宽表格留在纸面之内。
